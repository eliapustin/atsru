# Перенос сайта на хостинг

Актуально для схемы: основной сайт в корне домена, существующий WordPress в `/news/` на том же домене. Папка `news/` на хостинге содержит `wp-admin`, `wp-content`, `wp-includes`, `wp-config.php` и другие файлы WordPress. Локальные проверки новостей и форм выполнены; доставка писем в реальный ящик пока не проверена.

## Что подготовлено

- `wordpress/ats-static-site.zip` — `index.html`, `assets/` и `api/lead.php`. В архиве ссылки на новости ведут в `/news/`; локального адреса `astru-news.local` нет.
- `wordpress/ats-news-theme.zip` — тема для установки через админку WordPress.
- Локальная установка WordPress `astru-news.local` содержит пробные записи «Hello world!» и «Тестовый заголовок», два изображения и локальные URL. Её полный экспорт **не предназначен** для распаковки поверх WordPress на хостинге. Архив темы проверен: все девять файлов совпадают с исходниками, PHP-файлы проходят синтаксическую проверку. Тема требует WordPress 6.0+ и PHP 8.0+.
- Формы по умолчанию адресуют письма на `liap1990@gmail.com`; публичный контакт остаётся `aviatechnosoft@yandex.ru`. На внешнем домене обработчик требует настроенного адреса отправителя.
- Архив статической части не содержит WordPress, его базу данных и загруженные в WordPress медиа.

## Перед изменением действующего сайта

### Если `/news/` отвечает 403

Существующие файлы WordPress в `news/` ещё не подтверждают, что веб-сервер обслуживает этот каталог. До установки темы и замены `index.html`:

**Аудит копии `current/news` от 08.10.2026:** есть стандартный `index.php`, `wp-config.php`, каталоги ядра и `.htaccess`; версия в `wp-includes/version.php` — 7.1.3 (раньше панель показывала 7.1.2). Каталог `wp-content/uploads` пуст, темы только стандартные, `ats-news` не установлена. Базы данных в копии нет, поэтому адреса WordPress и наличие записей по ней не определить. В `.htaccess` указаны `RewriteBase /` и переход на `/index.php`, то есть правила для корня домена; если WordPress должен работать именно в `/news/`, эти правила нужно исправить после проверки адресов WordPress в базе. Сами правила не доказывают причину `403` для запроса `/news/`: на существующий каталог правило с условием `!-d` не срабатывает.

**Результаты запроса от 08.10.2026:** `/news/index.php` переходит на `/news/`, после чего сервер возвращает 403; `/news/wp-login.php` после входа переводит на корневой `/wp-login.php`, который даёт 404. Это согласуется с двумя независимыми настройками: веб-сервер не открывает `index.php` как индекс каталога `/news/`, а адрес WordPress `siteurl` в базе, вероятно, указывает на корень домена. В копии `wp-config.php` нет `WP_HOME` и `WP_SITEURL`; префикс таблиц — `wp_`. Точные значения `siteurl` и `home` нужно посмотреть в базе.

Для этой установки, после резервной копии папки `/news/`, её `.htaccess` и **базы данных**:

1. В панели управления базами открыть ту базу, к которой относится `/news/wp-config.php`, и таблицу `wp_options`. Найти строки `option_name = siteurl` и `option_name = home`. Если они указывают на корень `https://www.aviatechnosoft.ru`, изменить **обе** на `https://www.aviatechnosoft.ru/news` (без завершающего `/`). Если там уже `/news`, не менять базу и перейти к следующему пункту.
2. В настройках веб-сервера для каталога `/news/` указать `index.php` как индексный файл. При поддержке Apache `.htaccess` это можно сделать строкой `DirectoryIndex index.php` **перед** блоком `# BEGIN WordPress`; при ошибке 500 отменить строку и обратиться к хостингу с журналом ошибки.
3. После подтверждения адресов `/news/` заменить в копии `.htaccess` правила `RewriteBase /` → `RewriteBase /news/` и `RewriteRule . /index.php [L]` → `RewriteRule . /news/index.php [L]`. Для сверки подготовлен [пример полного `.htaccess`](../wordpress/news-htaccess.example), но **не загружать его вместо рабочего файла до проверки базы и резервной копии**. На хостинге сохранить исходный файл для отката. После восстановления доступа открыть **Настройки → Постоянные ссылки** и сохранить их: WordPress сгенерирует правила заново.
4. Проверить `/news/`, `/news/wp-login.php`, вход в `/news/wp-admin/` и одну запись. Если `/news/` всё ещё отвечает 403, передать поддержке хостинга точное время запроса и строку журнала веб-сервера; одна правка `.htaccess` не устранит запрет на уровне хостинга.

Отдельное предупреждение `Deprecated: Case statements followed by a semicolon ... phar:///usr/local/bin/wp/vendor/react/promise/...` относится к библиотеке **WP-CLI хостинга**, которую запускает панель. Выведенное после него `7.1.2` — версия WordPress, а не версия PHP. Это отдельная проблема совместимости инструмента с PHP (такое предупреждение добавлено в PHP 8.5); точную версию PHP для сайта нужно проверить в панели. Если предупреждение мешает панели, передать его поддержке хостинга. Не редактировать `/usr/local/bin/wp` и файлы WordPress вручную ради подавления сообщения.

### После восстановления доступа

1. Уточнить **фактический корень сайта** в панели хостинга и проверить, что показанные на скриншоте файлы относятся именно к нужному домену. Посмотреть скрытые файлы и правила веб-сервера (`.htaccess`, если используется): старые перенаправления могут влиять на `/news/` и новый `api/lead.php`.
2. Проверить, что существующий WordPress открывается по `https://ДОМЕН/news/` и доступна его админка по `/news/wp-admin/`. В **Настройки → Общие** проверить адрес WordPress и адрес сайта; для этой схемы оба должны вести в `/news/`. Не менять адреса наугад: сначала выяснить, нет ли настроенного особого размещения или перенаправлений.
3. Создать скачиваемую резервную копию **всего корня сайта**, включая скрытые файлы (`.htaccess`), папку `news/`, `wp-content/uploads`, `wp-config.php` и другие каталоги. Отдельно сохранить базу данных этого WordPress. Проверить, что копию можно открыть и в ней есть ожидаемые файлы. Не публиковать `wp-config.php` и дамп базы в репозитории.
4. Зафиксировать старые URL из `sitemap.xml` и важных внешних ссылок. Старые `product.html`, `education*.html`, `news.html` и другие страницы не входят в новый архив; решить, какие из них перенаправить на новые страницы, прежде чем удалять старые файлы.
5. Желательно собрать и проверить копию на тестовом домене или поддомене с тем же размещением `/news/`. До переключения действующего сайта убедиться, что PHP исполняется и в корне, и в WordPress; обработчику форм требуется PHP 8 или новее.

## Сборка и проверка на хостинге

1. В корне **тестового** сайта распаковать `wordpress/ats-static-site.zip`. Должны появиться `index.html`, `assets/` и `api/lead.php`. Папка `news/` и другие старые каталоги архивом не затрагиваются. Не копировать туда `index.html` и `assets/` из рабочего репозитория по отдельности: в них ссылки на `astru-news.local`.
2. Использовать **существующий** WordPress в `news/`. Не копировать туда локальные `wp-admin`, `wp-includes`, `wp-config.php` или базу LocalWP поверх рабочей установки. После резервной копии лучше сначала проверить копию WordPress на тестовом адресе. В админке загрузить `wordpress/ats-news-theme.zip`, посмотреть предварительный вид с существующими записями, затем активировать тему. Если админка недоступна, распаковывать архив темы можно только в `news/wp-content/themes/` так, чтобы получилась папка `news/wp-content/themes/ats-news/`; это не устраняет 403 и не активирует тему. В настройке темы «Адрес основного сайта» указать `https://ДОМЕН/`.
3. Проверить постоянные ссылки и открыть `/news/` и существующие записи. Если локальные новости были только пробными, не переносить их. Если там есть новые нужные материалы, переносить **только эти записи и медиа**, сохраняя действующую базу и старые публикации; XML-экспорт сам по себе не гарантирует перенос медиа с недоступного извне `*.local`.
4. Настроить серверную почту. Получатель уже задан как `liap1990@gmail.com`. Указать разрешённый хостингом адрес отправителя `ATS_LEAD_FROM` или создать `atsru-lead-config.php` **на один уровень выше публичного корня** по [образцу](lead-config.example.php). Не класть этот файл в публичную папку и не использовать адрес Gmail как `From` без соответствующей настройки почтового сервиса. Если на хостинге задан `ATS_LEAD_TO` или уже существует приватный конфигурационный файл, они переопределяют получателя из кода.
5. Отправить тестовые заявки с вымышленными данными, включая отмеченный пункт про КП. Проверить фактическое письмо во «Входящих» и «Спаме» `liap1990@gmail.com`: сообщение об успехе на сайте означает только принятие письма почтовой подсистемой.
6. Проверить с компьютера и телефона: главную, меню, изображения и видео; переходы из основного сайта в `/news/` и обратно; фото/видео новости; все формы и сообщения об ошибках. Проверить HTTPS и отсутствие ссылок на `*.local`.

## Переключение действующего сайта

После успешной проверки тестовой копии и резервной копии действующего сайта повторить публикацию в фактический корень рабочего домена либо переключить домен на проверенную копию — способ зависит от панели хостинга. При смене адреса тестового WordPress обновить его адреса и настройки темы, проверить ссылки и медиа. Сохранить старые файлы до настройки перенаправлений; файлы подтверждения поисковых систем (`google*.html`, `yandex*.html`) не терять. Обновить `sitemap.xml` и проверить старые адреса после переключения.

Текст политики обработки персональных данных в форме пока заглушка. До публичного запуска его нужно заменить на утверждённый текст и ссылку. Для проверки писем и настройки отправителя используйте [инструкцию по формам](forms-local-testing.md), для WordPress — [инструкцию по новостям](wordpress-news-setup.md).
